---

## Model Description

A three-component ensemble for predicting **Team Resilience Zone** (Green /
Yellow / Red) from collaboration metadata features.

| Component | Weight | What it captures |
|-----------|--------|-----------------|
| Isolation Forest | 30% | Point-in-time feature anomalies (unusual combinations) |
| LSTM (2-layer, hidden=64) | 40% | 14-day trend deterioration |
| AFS soft classifier | 30% | Domain-knowledge prior via AFS thresholds |

The ensemble averages the three probability vectors and predicts the argmax
class.  The AFS component uses sigmoid functions centered on the zone
boundaries (40 and 70) to produce a smooth prior.

---

## Input Features

| Feature | Range | Description |
|---------|-------|-------------|
| `calendar_density_score` | [0, 1] | Meeting saturation per working day |
| `after_hours_activity_index` | [0, 1] | Fraction of activity occurring outside core hours |
| `context_switch_count` | [0, 1] | Task fragmentation (back-to-back meetings + repo switches), normalized |
| `sprint_health_index` | [0, 1] | Delivery health — story points + PR cycle time (higher = healthier) |

The **LSTM** receives 14-day rolling windows of the 4-feature vector.
The **Isolation Forest** and **AFS** components receive the current day's
4-feature vector (last timestep of each sequence).

## Output

| Output | Type | Description |
|--------|------|-------------|
| Predicted zone | int (0/1/2) | 0 = Green, 1 = Yellow, 2 = Red |
| Class probabilities | float[3] | Softmax-normalized ensemble probabilities |

---

## Resilience Zone Definitions

| Zone | AFS Range | Meaning | Recommended Action |
|------|-----------|---------|--------------------|
| 🟢 Green | 0–39 | Healthy team — no intervention needed | Monitor quarterly |
| 🟡 Yellow | 40–69 | Elevated risk — monitor more closely | Weekly check-in |
| 🔴 Red | 70–100 | High risk — intervene | HR escalation within 48h |

---

## Training Data

**Current:** Synthetic digital exhaust data generated by `SyntheticDataGenerator`
with 80 teams × 90 days and default zone distribution (55% Green, 30% Yellow,
15% Red).

**Future:** Real training data will replace synthetic data once the Kafka
ingestion pipeline (Sprint 1–2) and ETL enrichment (Sprint 3) have accumulated
≥ 30 days of team telemetry in the feature warehouse.

Temporal split used:  **70% train / 15% val / 15% test** (chronological — no
random splits to prevent data leakage across time).

## Evaluation Criteria & Results

### CI Acceptance Thresholds

| Metric | Threshold | Rationale |
|--------|-----------|-----------|
| Red Zone precision | ≥ 0.80 | Minimize false alarms fatiguing HR teams |
| Red Zone recall | ≥ 0.75 | Catch real at-risk teams before attrition occurs |
| Green Zone FPR | ≤ 0.10 | Avoid unnecessary interventions on healthy teams |

### Evaluation Procedure

Run the evaluation script:
```bash
python -m ml.evaluation.evaluate --n-teams 80 --n-days 90 --seed 42
```

Results are written to `ml/models/v1.0/metrics.json`.

## Limitations

- **Cold start:** Teams with fewer than 14 days of data cannot produce LSTM
  sequences.  For cold-start teams, fall back to the Isolation Forest + AFS
  components only (handled in `ml.inference`, Sprint 6).

- **Synthetic training:** The model is trained on synthetic data calibrated
  from domain assumptions.  Accuracy on real-world data will differ until
  retraining is performed with warehouse data.

- **Label quality:** Zone labels are derived from AFS thresholds, which are
  calibrated on domain knowledge, not validated clinical burnout diagnoses.
  The model predicts operational risk, not medical burnout.

- **Team-level only:** All inputs are team-level aggregates.  The model cannot
  identify at-risk individuals — this is an intentional privacy constraint (see
  `docs/adr/003-privacy-aggregation.md`).

## Privacy Constraints

- Inputs are metadata aggregates only; no message bodies or document contents.
- Outputs are surfaced at team granularity only — never for individual users.
- Model artifacts are stored in `ml/models/` and must not be committed to
  public repositories.
- Every inference call must be audit-logged per `docs/adr/003-privacy-aggregation.md`.
